# PULSE benchmark -- bttger six-endpoint contract (2026-11-01)

**Date:** 2026-11-01. **Repository:** `main` at `0956532` plus this benchmark
unit (the driver gained a duration mode; the raw JSON is committed).
**Toolchain:** compiler **v0.65.4** + stdlib **407c92d**, `xiom.pulse` 0.3.2,
`xiom.http` 0.1.11. **Status:** current baseline, not a cross-framework
ranking. Raw autocannon output is committed under
`benchmarks/bttger/results/`.

This report supersedes the 2026-10-19 baseline for *current* numbers; the old
report remains in `REPORT.md` as the v0.64.8 baseline. The two are not a
controlled A/B (different toolchain and sampling method).

## 1. What was measured

The six-endpoint interface from `E:\repos\web-framework-benchmarks` (bttger,
MIT; `OPEN_API_DEFINITION.yaml`) implemented by `benchmarks/bttger/main.xi`
on the published Beacon core (`xiom.pulse` 0.3.2, `app.register` +
`app.serve`), not the product Station server.

| Endpoint | Contract work |
|---|---|
| `GET /serialize` | `{"message":"Hello, World!"}` |
| `GET /serialize/big` | nested object + 50 on-demand publication entries |
| `GET /plain/text` | `Hello, World!` as `text/plain; charset=utf-8` |
| `GET /query/300/tools/10?...` | path/query/header validation, JSON response with ISO timestamp |
| `POST /insert` | parse JSON, add `id` + `createdAt`, re-serialize, `201` |
| `GET /calculate` | recursive `fib(27)` (0/1 seed, as in the reference gin app) |

## 2. Method

- **Tool:** `autocannon` 7.15.0 (the bttger suite's tool), Node v23.10.0.
- **Server:** Windows native `out/bench_bttger.exe`, built from
  `benchmarks/bttger/main.xi` with the pinned XIOM **v0.65.4** + stdlib
  **407c92d**; keep-alive on; read/write deadlines 30000 ms; idle deadline
  120000 ms (the higher idle value stops the harness's waiting connections
  from being closed between cycles; it does not add concurrency). Access log
  off (`PULSE_LOG=0`), no TLS, no compression, no database.
- **Host:** Windows 11 Pro (10.0.26300), AMD Ryzen 9 3950X (16 cores / 32
  logical CPUs); the load generator runs on the same host; no containers.
- **Load:** **5 seconds per endpoint** after a 5-second warmup on
  `/serialize`, endpoints run sequentially. Two connection modes: **1** and
  the reference suite's **10**. Duration mode (rather than a fixed request
  count) keeps the windows long enough for stable averages while bounding
  the memory cost of the known per-request retention.
- **Memory:** the server process WorkingSet64 is sampled every 200 ms during
  the run; a 2048 MB watchdog would stop the run (it did not trigger).
- PULSE sends its default security headers on every response; no response
  compression is enabled.

## 4. Results -- ten connections (reference-suite shape)

`BENCH_CONNECTIONS=10`, same duration. Throughput is **unchanged within
noise**; no timeouts appeared in a 5-second window. The sequential-accept
loop serves one accepted connection at a time, so extra connections queue
rather than add capacity. Longer runs at larger amounts turn that queueing
into timeouts (see the 2026-10-19 report); the architectural fix is the
worker supervisor in the grant (WP4).

## 5. Memory

| Run | RSS start | RSS end | peak | responses | growth/response |
|---|---:|---:|---:|---:|---:|
| c1, 5 s | 4.5 MB | **855.7 MB** | 855.6 MB | 32,011 | **~26.6 KB** |
| c10, 5 s | 4.5 MB | 854.4 MB | 853.9 MB | 31,452 | ~27.0 KB |

This is the known per-request retention floor, not a soak result. The
response-builder and per-connection-read-buffer work already landed (the
pure build path is flat); the remaining retention is compiler reclamation of
maps/strings/JSON values plus app-path router/header lookups. The grant's
WP1 turn this into a **24-hour, 100 req/s gate with an RSS ceiling**; the
1,000,000-request run stays blocked until that gate is met. A benchmark run
must not be used as a memory-safety claim.

## 6. Findings

1. **No scale-out from connections.** c10 is within noise of c1 on every
   endpoint. The single-accept loop is the ceiling; the fix is the process
   supervisor / multi-process service loop (SO_REUSEPORT on Linux, N ports
   on Windows), which is WP4.
2. **Payload cost is visible.** `/serialize/big` (50 entries built per
   request) is ~4.6x slower than the tiny `/serialize`; `/insert` (JSON
   parse + rebuild) and `/query` (path/query/header validation) sit between.
3. **`/calculate` blocks the loop.** `fib(27)` costs ~2.6 ms per request on
   this host; a compute endpoint belongs on a worker/thread boundary. The
   c10 p99 stays low here because the queue is short in a 5 s window.
4. **All clean-path responses were 2xx**, with zero errors in both modes.
5. **The current pin is substantially faster than the October baseline**
   (table below). This is not a controlled A/B: the toolchain moved from
   v0.64.8 to v0.65.4 and the sampling moved from 5,000 requests to 5 s.

## 8. Reproduction

```powershell
# build the contract app (Beacon only; no SQLite C source)
. .\scripts\dev-env.ps1
.\scripts\build.ps1 benchmarks\bttger\main.xi -Name bench_bttger

# start the server (port 18090 avoids local listeners)
$env:PULSE_PORT = "18090"
$env:PULSE_IDLE_TIMEOUT = "120000"
$env:PULSE_LOG = "0"
Start-Process .\out\bench_bttger.exe

# in benchmarks\bttger (autocannon is installed from package.json)
$env:BENCH_PORT = "18090"
$env:BENCH_DURATION = "5"
$env:BENCH_CONNECTIONS = "1"
$env:BENCH_WARMUP = "5"
node benchmark.js xiom-pulse-windows-2026-11-01-c1-5s

# repeat with BENCH_CONNECTIONS=10 and a different title
```

## 9. Limitations

- Single host; the load generator shares the CPU with the server. Absolute
  rates are indicative, comparisons across endpoints are meaningful.
- Windows only in this run; no TLS, no compression, no database.
- 5-second windows; not a soak and not the 1,000,000-request run.
- No cross-framework comparison; the suite and methodology are the bttger
  reference, but the peer implementations were not run here.
- The memory growth is a known blocker, not a benchmark feature; do not
  quote this run as evidence of stable memory.

## Post-report update (2026-11-06)

`route_match` no longer rebuilds the 25-route registry router per request;
the table is built once and cached. A 60 s `/health` keep-alive probe on the
same Windows host measured the steady floor at **20.6 -> 16.1 KB/req** (95
steady requests); the longer v0.65.6 reference is 17.6. The remaining floor
is the request/response and Map path plus the deferred Option aggregate. The
24 h/1M gates are still open; do not treat this as soaked.

A further 2026-11-06 cut skips the gate's route match unless per-route rate
policy is enabled; two 60 s runs measured 15,597.6 / 15,499.6 B/req
(15.2-15.6 KB). See `docs/MEMORY-FLOOR-2026-11-06.md`.
